# Сценарий защиты презентации

## 1. Elevator pitch на 30 секунд

`VeyraFlow` — это desktop-приложение для отслеживания состояния выбранных файлов и папок, ведения истории версий и восстановления нужного состояния. Система создает snapshots, хранит версии файлов в блочном виде с дедупликацией, умеет сравнивать текст, изображения и часть других форматов, работает локально без интернета и при необходимости синхронизирует данные с облаком. В архитектуре разделены UI на C# и Avalonia, application/use-case слой на .NET, производительное native-ядро на Rust и облачный REST API на Go.

## 2. Какие слова лучше не использовать

Не использовать:

- `файловый менеджер`
- `замена Windows Explorer`
- `проводник`
- `организация файлов`
- `перемещение и переименование файлов`
- `drag-and-drop управление файлами`
- `полноценный semantic diff для всех форматов`
- `полный cloud restore history уже реализован`
- `gRPC уже является основной облачной шиной`

Использовать вместо этого:

- `desktop-приложение для отслеживания состояния файлов`
- `система snapshots и истории версий`
- `versioned monitoring для выбранных директорий`
- `сравнение версий и восстановление файлов`
- `offline-first desktop application`
- `частично реализовано`
- `заявлено, но требует доработки`

## 3. Главная линия выступления

Сильная версия защиты строится на трех идеях:

1. Это не проводник, а система контроля состояния файлов и исторических версий.
2. Главное техническое ядро проекта — snapshots, block storage, дедупликация и restore.
3. Архитектура разделяет локальную работу, native performance layer и облачную синхронизацию.

## 4. Краткий сценарий на 7 минут

### Слайд 1. Титул

Говорить:

`Тема моего проекта — VeyraFlow. Корректно его описывать не как файловый менеджер, а как desktop-приложение для отслеживания состояния выбранных файлов и папок, ведения истории версий, сравнения версий и восстановления нужного состояния.`

Переход:

`Сначала покажу, какую практическую задачу решает система и почему эта задача актуальна.`

### Слайд 2. Цель и задачи

Говорить:

`Цель проекта — создать локально автономную систему snapshots для выбранных директорий, которая фиксирует изменения файлов, хранит версии экономно за счет дедупликации и позволяет быстро восстановить нужное состояние. Отдельная задача — не привязывать основную работу к интернету и облаку.`

Переход:

`Почему это актуально: многие решения либо ориентированы на синхронизацию, либо на резервное копирование, но не дают удобную локальную историю изменений на уровне версий файлов.`

### Слайд 3. Актуальность

Говорить:

`Пользователь работает с документами, кодом, изображениями, медиафайлами. Изменения происходят часто, а обычные папки не сохраняют историю состояния. Поэтому нужна система, которая не заменяет проводник, а добавляет слой наблюдения, истории и восстановления.`

Переход:

`Чтобы точнее понять нишу проекта, я сравнил его с существующими аналогами.`

### Слайд 4-5. Аналоги и сравнительная характеристика

Говорить:

`VeyraFlow не повторяет один-в-один ни OneDrive, ни Git, ни классические backup-средства. От облачных sync-решений он отличается локальным offline-first режимом. От Git — ориентацией не только на текстовый код, но и на бинарные и мультимедийные файлы. От резервного копирования — наличием истории версий, diff и восстановления отдельных файлов, а не только образов.`

Переход:

`Теперь покажу основной технический pipeline: как из обычного файла получается snapshot и история версий.`

### Слайд 6. Этапы сохранения файла

Говорить:

`При создании snapshot система вычисляет SHA-256 для версии файла, разбивает содержимое на фиксированные блоки по 64 КБ, затем для native block storage использует BLAKE3 для ключей блоков. Если блок уже существует, он переиспользуется. Если нет, сохраняется в block storage. В SQLite сохраняются не сами файлы, а метаданные: snapshot, file version и ссылки на блоки.`

Простое объяснение:

`То есть система хранит не полные копии каждой версии, а набор блоков, из которых потом можно собрать исходный файл обратно.`

Переход:

`Эта цепочка встроена в многослойную архитектуру, где каждый слой отвечает за свою задачу.`

### Слайд 7. Архитектура

Говорить:

`UI реализован на C# и Avalonia по MVVM. Application layer на .NET использует CQRS и MediatR. Native производительные операции вынесены в Rust через P/Invoke: это scan, часть diff и block storage. Облачная часть реализована как REST API на Go с PostgreSQL. Благодаря этому UI не работает напрямую ни с SQLite, ни с Rust, ни с облачным API.`

Переход:

`На следующем слайде я покажу, какие форматы реально поддерживаются и где поддержка специализированная, а где generic.`

### Слайд 8. Поддерживаемые форматы

Говорить:

`Наиболее зрелая поддержка сейчас у text diff и image diff. Для Word OOXML есть частичная семантическая проекция. Для части аудиоформатов реализован preview-diff на основе waveform и спектральных метрик. Для остальных форматов система все равно хранит версии и умеет восстанавливать файлы, но сравнение может быть generic binary.`

Важно добавить устно:

`Некоторые форматы в презентации лучше трактовать аккуратно: например, FLAC и OGG в текущем коде отслеживаются, но не routed в специализированный audio diff.`

Переход:

`Теперь коротко о том, почему был выбран именно такой стек технологий.`

### Что добавить в устное объяснение про дедупликацию

`Если у двух версий файла совпадают блоки, система не сохраняет одни и те же данные повторно. Поэтому история версий растет намного экономнее, чем при хранении полных копий каждого состояния.`

### Что добавить в устное объяснение про restore

`При восстановлении система берет список блоков версии, сортирует их по порядку, читает каждый блок из storage, распаковывает или расшифровывает при необходимости и последовательно собирает исходный файл. После этого проверяется итоговый SHA-256 восстановленного файла.`

### Что добавить в устное объяснение про image diff

`Для изображений система не ограничивается только hash-сравнением. Она умеет показывать визуальную разницу: overlay, heatmap, split-view и changed regions.`

### Что добавить в устное объяснение про offline-first

`Основные функции системы не зависят от облака. Даже без авторизации и без интернета пользователь может создавать snapshots, сравнивать версии и восстанавливать файлы. Сеть нужна только для дополнительной cloud sync-функциональности.`

## 6. Как объяснить сложные части простыми словами

### 6.1 Что такое snapshot

`Snapshot — это снимок состояния выбранной директории в конкретный момент времени: какие файлы были, какие версии они имели и как они были связаны с блоками данных.`

### 6.2 Что такое FileIdentity

`FileIdentity — это логическая карточка файла внутри репозитория, например относительный путь и имя.`

### 6.3 Что такое FileVersion

`FileVersion — это конкретное содержимое этого файла в определенный момент времени.`

### 6.4 Что такое FileVersionBlock

`FileVersionBlock — это один из блоков данных, из которых состоит версия файла.`

### 6.5 Как объяснить блоки

`Представим, что файл разрезали на одинаковые куски по 64 КБ. Если кусок уже есть в хранилище, его не сохраняют заново. Поэтому новая версия файла может состоять частично из старых блоков и частично из новых.`

### 6.6 Как объяснить image diff

`Система не только хранит изображение, но и умеет сравнивать две версии как картинки: сколько пикселей изменилось, где находятся зоны изменений и как это показать визуально.`

### 6.7 Как объяснить audio diff

`Для части аудиоформатов система строит не текстовый diff, а сравнение сигнала: waveform, спектрограмму и интервалы, где звук реально изменился.`

### 6.8 Как объяснить generic binary

`Если для формата нет специального diff, система все равно хранит и восстанавливает версии, а сравнение показывает на уровне размеров, hash и overlap блоков.`

## 7. Как объяснить выбор C#, Rust и Go

### C#

`C# и .NET используются там, где важны архитектура приложения, MVVM, CQRS, DI и удобная интеграция desktop UI с локальной persistence-логикой.`

### Rust

`Rust вынесен в native core для производительных и безопасных операций над бинарными данными: scan, block storage, часть diff и compression-related задач.`

### Go

`Go использован для cloud API, потому что он хорошо подходит для компактного REST-сервиса, фоновой обработки sync и работы с PostgreSQL.`

## 8. Что отвечать, если спросят о неполной готовности

Готовая честная формулировка:

`В проекте есть зрелое ядро: snapshots, block storage, deduplication, restore, text diff, image diff, offline-first desktop flow. Часть функций находится на более ранней стадии: например полный cloud history restore, расширенный semantic diff Word внутри собственного UI и универсальная audio/video поддержка для всех кодеков. Я намеренно не называю эти части полностью завершенными.`
